OpenHands 集成到 Atlas — 三种深度，三种代价

Apache 2.0 · Python 原生 · pip install openhands-ai

A

SDK 嵌入 — pip install 直接 import

Atlas 后端安装 openhands-ai 包，在 FastAPI 中 import Agent/Tool，作为模块调用。

Pros

  • 最深集成 — 一个进程，零网络延迟
  • 可用全部 SDK 能力（Agent/Tool/Conversation）
  • SSE 流式直通前端

Cons

  • 需 Docker daemon（沙箱）
  • SDK 版本更新需适配
  • 依赖较重（openhands-ai 约 200MB）

工期 5-7 天 · 代码 ~800 行 · 最推荐

B

独立服务 — OpenHands 单独跑，REST API 调用

OpenHands 以独立 Docker 容器部署，Atlas 通过 HTTP API 向它发任务。

Pros

  • 解耦 — 独立升级/重启
  • Atlas 改动最小
  • 可绕过 SDK 版本适配问题

Cons

  • 需维护两个服务
  • 网络开销 + 单点故障
  • 用户体验割裂（两个系统）
  • OpenHands REST API 不够成熟

工期 3-4 天 · 浅集成 · 不建议

C

源码裁剪 — 只复制 Agent Loop 核心模块

把 OpenHands 里的 agent/、tools/ 目录摘出来，移植到 Atlas 的 api/app/ 下。

Pros

  • 最小依赖 — 只取所需
  • 完全可控 — 自己的代码
  • 包体积最小

Cons

  • 需要深度读懂 OpenHands 源码
  • 裁剪后要补胶水代码
  • 后续 OpenHands 更新无法受益
  • 实际就是方案B"选择性移植"的变体

工期 8-10 天 · 维护成本高 · 除非有特殊定制需求

🎯 推荐方案 A：SDK 嵌入

理由：OpenHands 设计就是为了以 SDK 方式嵌入其他应用的。你的 Atlas 后端加一个 agent_service.py，import OpenHands SDK，用 FastAPI 的 StreamingResponse 把 Agent 执行过程 SSE 推到前端。这是它文档中的推荐用法。

具体改动范围（方案 A）

层级 文件 改什么 工作量
新增 api/app/agent_service.py 封装 OpenHands Agent + Tool 注册 + 事件流 1.5 天
新增 api/app/routers/workspace.py POST /workspace/run · GET /workspace/files · SSE 流式 1 天
修改 api/app/main.py 注册路由 · CORS 确认 0.5 天

修改 docker-compose.yml 加 Docker socket 挂载 0.5 天
新增 web/src/Workspace.tsx 开发工具页面（代码编辑器 + 终端 + 文件树） 2 天
修改 web/src/App.tsx 加导航路由 + Workspace 入口 0.5 天
