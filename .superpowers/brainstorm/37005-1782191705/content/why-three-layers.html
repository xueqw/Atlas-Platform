为什么需要第三层 Skill Workers？

Planner Agent 不能直接执行吗？

核心矛盾：Planner 不能既是"指挥官"又是"士兵"

❌ 两层（Planner 直接执行）

Planner 收到任务：
"分析销售数据 + 生成周报"

→ Planner 自己读CSV
→ Planner 自己跑pandas
→ Planner 自己写markdown

问题来了：
1. Planner 必须装 pandas、matplotlib、python-docx... 所有工具
2. 数据清洗出bug，整个Planner卡住
3. 换一个skill要改Planner代码
4. 一个长任务吃掉整个上下文窗口

✅ 三层（Planner → Workers）

Planner 收到任务：
"分析销售数据 + 生成周报"

→ Planner 拆成3步，分派出去

Worker_A (清洗): 只装pandas
Worker_B (分析): 只装matplotlib
Worker_C (报告): 只装python-docx

好处：
1. 每个 Skill 独立环境，互不污染
2. 某个 Skill 挂了，只重试那一步
3. 新增 Skill 零侵入
4. 可并行执行，上下文隔离

三个降不下来的原因

A

上下文隔离

Planner 的上下文窗口是有限的。如果它亲自执行一个"分析10万行CSV"的skill，中间结果就会把对话历史冲掉。Worker 独立执行，只把结论返回 Planner。

B

失败隔离

一个 3 步任务，Worker_B 在第二步挂了。三层架构：重试 Worker_B 即可。两层架构：整个 Planner 状态丢失，从头再来。

C

可扩展性

加一个新 skill（比如"图片生成"）需要修 Planner 代码吗？三层：注册一个新 Worker 即可，Planner 感知能力。两层：Planner 代码膨胀，迟早不可维护。

本质：向心力 vs 离心力

Planner = 向心力 — 理解意图、做决策、定方案
Workers = 离心力 — 把具体工作撒出去，独立完成

判断标准：如果 Planner 需要为某个 skill 装特定
依赖包 → 说明应该拆成独立 Worker。

现实中你已经在用三层

你现在的 Claude Code 会话本身就是三层架构的实例：

Atlas 层 实际角色
Planner Agent你 — 决定让 Claude 做什么
Skill WorkersClaude Code 的 Agent 子进程 — 各自独立执行，互不干扰
MCPClaude Code 调用的外部工具服务器

你不会自己手写代码——你让 Claude 去写。同理，Planner 不该自己执行 skill——它调度 Worker 去执行。
